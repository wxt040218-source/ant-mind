# Ant Mind 经营与增量机制实施规格

编写日期：2026-11-08（Asia/Shanghai）。基于[当前 v0.12 规格](MVP_SPEC.md)、实际代码和[游戏内核调研](GAME_KERNEL_RESEARCH.md)。

状态：开发前详细规格草案。用户本轮要求写清“怎么在游戏里做”，本文件不代表功能已经实现；原游戏规格仍以 MVP_SPEC.md 为准。以下数值为建议的可配置原型值，不是平衡结论。接口名为拟定名称，尚不能直接调用。

## 1. 要做出的游戏体验

玩家说“提高每分钟食物收入”。Agent 探索地图，发现果丛与危险区域，组织不同小组，建立集货点；再决定是否加工成便于运输的补给，用成果发展蚁群和科技。玩家能看见蚂蚁搬东西、设施建设和生产、食物流向，以及收入改善。

所有战略规划交给 Agent。继续维持：每蚁种一份共享程序，个体独立记忆；小组是自由任务参数和命名地点，不新增按组／按个体编程。采集队、运输线、补给站、狩猎队都是 Agent 组织出来的策略，不是引擎预设工作流。

一期仍使用侦察、搬运、兵蚁三种职业。所有职业原则上都能做满足能力要求的基础动作；身体参数影响效率。暂不为每个新设施增加一个新职业。

## 2. 范围和开发顺序

| 阶段 | 交付内容 | 完成后能玩什么 |
|---|---|---|
| M0 | 完整存档／继续、分支评估、效率统计 | 能保存长期蚁群，对同一局面比较算法 |
| M1 | 物品批次与计分基础、果丛／纤维源、显式采收 | 经营固定资源点，形成持续采集路线 |
| M2 | 施工地点、中转箱、存取／转交 | Agent 自己建设前线仓库、组织接力和补给 |
| M3 | 一种加工台、两份配方、加工工作状态 | 原料进入加工，再运回／用于补给 |
| M4 | 能力型科技、身体模块、受限共享存储／计算储备 | 相同世界出现不同构筑和算法 |
| M5 | 环境周期、挑战场景、新区域开拓 | 根据环境换策略，形成长期目标 |

先完整实现 M0～M3，构成第一版经营闭环。M4～M5 保留明确扩展入口，后续逐项推进，不与第一批一起堆进游戏。离线发展与强制重生不列入首批。

## 3. M0：保存与公平评估

### 保存什么

- 世界 Tick、确定性随机状态、所有 next ID、实际内容配置与内容版本／哈希。
- 全部独立对象，包括未发现对象、死亡记录、源头、物品所有权、建筑和生产中的原料。
- 各蚁种程序的源码、版本历史、当前版本和待应用版本；恢复时重新校验并编译。
- 每只蚂蚁的位置、负载、记忆、通信缓存、动作／冷却／进行中的操作。
- 经济、等级、科技、小组、认领、任务参数、统计计数器和里程碑。

保存从 actor 获取一致的不可变快照，文件写入由存储适配器完成；临时文件完整写成后原子替换。加载先完整校验，失败保留当前世界；暂停状态下通过 actor 一次替换，加载后仍暂停，关闭期间不推进模拟。玩家至少一个手动槽，Agent 可以创建命名检查点；首批不把完整事件回放或离线发展塞进存档阶段。

不能用公开 Snapshot 代替完整存档，它经过信息过滤且缺少恢复所需真值。MCP 只返回存档 ID 和元数据，不把原始世界文件作为观察接口返回。

加载生成新的 WorldInstanceId，命令同时携带期望世界 ID 与 revision。幂等键按世界实例区分，加载前的旧命令不能作用到加载后的世界；不能恢复旧 revision 后误接受旧写入。连接心跳等临时状态不从存档恢复。

### 怎么比较算法

保存检查点 → 离线评估器分别加载相同状态和程序 A／B → 各运行相同 Tick → 比较结果。评估分支不写正在玩的桌面世界，也不向 Agent 泄露未发现对象。再用多个种子／多个完整分钟窗口复测。

拟新增管理接口：save_game、list_saves、load_game、evaluate_program。评估要求指定算法、起始检查点和运行 Tick；超出上限拒绝，报告真实运行样本长度。

## 4. M0：收益与瓶颈统计

一分钟始终为 1200 个模拟 Tick，1／2／5 倍速只改变等待时长。前 1200 Tick 以内明确标注样本长度，不能当完整一分钟结论。

| 指标 | 定义与用途 |
|---|---|
| 新增原始食物首次入巢点数／分钟 | 首要资源收入指标，不因重复运输或加工刷高 |
| 首次入巢实物数量，按类型 | 看水果、肉、加工品实际进入巢穴的数量 |
| 库存净变化，按类型 | 区分赚得多和花得少 |
| 原料采收、加工投入／产出 | 判断卡在源头、运输还是加工 |
| 移动、交互、战斗、进食、空闲 Tick | 来自真实动作状态，不猜测代码的战略意图 |
| 失败动作及原因、预算消耗／超限 | 判断空跑、冷却重试、过时资源缓存和计算瓶颈 |
| 蚂蚁损失、治疗支出、设施停工 | 观察高收入背后的成本 |

统计按全群／蚁种／发生动作时所属小组汇总，换组不改写历史归属。提供滑动窗口及最近若干个完整分钟。不要把成功拾取、反复放下或毛搬运次数直接当净收入。

UI 仅显示概览和可展开统计，MCP get_statistics 可指定窗口、指标和维度；没有自动替 Agent 选择策略的“最优分工”按钮。

## 5. M1：统一物品与所有权

现有 FoodStore 和 Carry 数字不够表达跨库存转运和加工。新增 ItemDefinition、ItemLedger、ItemBatch／Segment；所有实际物品在任一时刻只有一个持有位置。

持有位置包括源头成熟物、地面食物、蚂蚁负载、巢穴、箱子、施工材料、加工输入、加工在制品和加工输出。账本保存权威数量和持有关系，物体保存位置／状态和 HolderId；对象详情、FoodStore 兼容视图和 UI 总数从账本派生，不保留第二套可独立修改的数量。

每只蚂蚁一期仍只携带一种物品类型，但允许同类不同批次。原料来源、可计分份额、已入巢状态在移动、分割、合并、加工和掉落时保留。已耗尽对象按现有规则保留记录，后续增加明确的归档策略。

| 初始物品 | 可食用 | 单位搬运质量 | 治疗量 | 主要用途 |
|---|---|---:|---:|---|
| fruit 水果 | 是 | 1 | 3 | 初始发展和基础补给 |
| meat 肉 | 是 | 1 | 6 | 补给和后续身体强化 |
| fiber 纤维 | 否 | 1 | 0 | 箱子与加工台施工 |
| fruit_concentrate 浓缩果食 | 是 | 1 | 6 | 两份水果压缩成一份便于运输的补给 |
| protein_meal 肉食补给 | 是 | 1 | 12 | 两份肉压缩成一份补给 |

食物总量只汇总可用于相应用途的物品。引入纤维后，不能继续把所有库存类型加总用于产卵／回血。旧发展配方限定原水果／肉；加工品能否支付具体升级由配方明确注册，不能按物品份数隐式等价。

### 守恒与计分必须先统一

对每个物品类型分别核对：初始量＋自然新生＋配方产出＝所有持有者当前量＋进食消耗＋建设消耗＋升级消耗＋配方投入＋明确销毁量。配方不同物品之间转换通过投入／产出账目闭合，不要求加工前后的“物品件数”相同。

原始食物首次入巢点数独立于件数、治疗量和营养。原水果／肉每份各生成一份原始计分额度；初始公共库存没有可再次计分额度。纤维不计食物分。未采收的自然生成总量继续不向外公开。

中转、转交不记入巢；第一次进入巢穴才结算对应份额，并将其可计分额度置零。取出再运回、掉落再拾取不重新生成额度。加工输出最多继承本次投入仍未结算的额度，不新造额度：2 份未入巢水果→1 份浓缩果食，仍只值 2 点；已计分水果加工后再入巢为 0 新点。输入混合已计分和未计分批次时逐段保留来源。

首批配方为 2→1，计分额度可用整数完整表达。通用批次拆分按累计比例分配、最后份额接收余数，不因拆分顺序增发额度；合并不能重算总额度。所有转运与加工通过单一 InventoryTransactions 入口完成。初始巢穴库存没有可重复计分额度；初始外部成熟食物仍可首次入巢计分。活跃批次和片段进入快照，耗尽且不再被引用的片段汇总进审计计数并归档，ID 不复用；不能无限保留每份历史物料导致长期游戏内存持续增长。

## 6. M1：果丛与材料源

新增 source 独立对象：Id、SourceType、Position、成熟容量、成熟物库存／持有者、恢复周期、下一次生长 Tick、剩余可采储量（非再生材料使用）、发现／最近观察记录、扩展属性。

### 原型初值

- 正式地图仍 128×128；生成 8 个果丛和 4 个纤维源，位置由种子决定、不重叠。
- 至少一个果丛距巢穴约 5 格，能被初始侦察蚁看到；其他点分散到不同距离。初始观察仍真实执行，不直接显示全图。
- 果丛最多有 5 份成熟水果，每 100 Tick 恢复 1 份；满额时该次产出跳过，不积累隐藏的补发额度。
- 纤维源初始储量建议 30，不自动恢复。一期建设规模受真实材料限制；再生材料或种植在后续扩展。
- 原地面随机小食物保留为低频散落补充，持续经营主要依靠果丛。迁移时调低散落刷新权重，具体比例集中配置，不能无意叠加两套满额产出。

生长产生实际成熟物时计入内部自然新生账目；harvest 只是从源头转到负载，不再次“生成”。敌人击败后按原规则生成肉批次，来源与计分额度正确初始化。

蚂蚁执行 harvest(source_id, quantity)，引擎检查一格范围、容量、物品类型、成熟数量和交互冷却，成功量为实际可转移量。不自动去资源点、不自动返回、不自动连续采。空源返回 source_not_ready 等明确结果，程序决定等待还是换目标。

可见记录必须有 LastObservedTick；未知源头不查询，视野外只返回旧记录。侦察蚁只有显式上报后才进入蚁后知识；组内其他蚂蚁要显式下载才得到更新。

## 7. M2：施工与中转箱

新增 building 对象：类型、位置、生命、施工状态、材料持有者、已完成工时、输入／输出持有者、容量／质量限制、当前工作、扩展属性。

Agent 调用 plan_build 指定地图内坐标，先创建不占物理空间的施工蓝图；此命令不检查未知占位物、不扣远处物品、不直接建成。蓝图上限建议 64，所有者可以看到自己的计划，但计划不能作为探测隐藏对象的工具。蚂蚁到场并局部观察后，才验证占地条件并给出真实施工状态；冲突则停止施工，不能在远处提前返回隐藏对象详情。首批设施不阻塞蚂蚁移动，障碍与寻路另作后续机制，避免在这一版隐含改变平面地图规则。

蚂蚁先把纤维真实搬到施工点，然后调用 work(building_id)。原型建议箱子需要 6 纤维、100 工时 Tick；加工台需要 12 纤维、200 工时 Tick。每次 work 操作持续最多 10 Tick，忙碌期间不能移动或做第二个物理动作，完成后需程序再次调用。首批每设施一个工作位，重复发命令不并行叠加效率。

材料真实保存在施工点，全部材料就绪才允许完成；建成时原子转入建设消耗账目。取消未完工地点把现存材料留作可取物，不全额生成“退款”。完整建筑拆除的回收比例配置化且不超过已投入材料，不能复制库存。

中转箱原型容量 40 单位质量，可混放不同物品；每种类型仍独立记账。它不扩大蚁后通信范围，不让远处蚂蚁自动知道库存。箱子容量、最后已知内容和最近观察时间进入合法投影。

库存移动动作：deposit(holder_id,item_id,quantity)、withdraw(holder_id,item_id,quantity)、transfer(ant_id,item_id,quantity)。仅一格内可执行，受负载与目标空间限制；一期允许部分成功，结果返回实际转移数量。数量非正数、无库存、满载、距离不符等明确失败。转交必须目标活着、同一蚁群且能装下。

任何采集线、接力和补给路线都由 Agent 用小组参数／共享代码实现。箱子没有自动派工、自动拉货或隐形运输功能。

## 8. M3：一种加工台，两份配方

加工台有输入、在制、输出三个真实持有位置，容量建议输入 20、输出 20；首批一个工作位。没有必要先加厨师职业。

| 配方 | 输入 | 输出 | 工时 Tick | 基础收益 |
|---|---|---|---:|---|
| 浓缩果食 | 2 水果 | 1 浓缩果食 | 100 | 同等治疗量，运输质量减半 |
| 肉食补给 | 2 肉 | 1 肉食补给 | 100 | 同等治疗量，便于前线补给 |

加工不会无条件优于直接运输：消耗设施、建设材料和蚂蚁工时。近距离采集可能直接送回更划算，远距离或前线补给才可能受益，交给 Agent 判断。

程序调用 process(building_id,recipe_id) 尝试启动一个批次：检查已解锁配方、设施类型、完整输入、空闲工作位和可容纳输出；条件满足才把原料从输入移到在制，保留批次来源。后续 work 按实际操作推进工时，完成时原子转换成输出。没有蚂蚁工作就暂停，不凭设置配方自动产出。

worker 离开／受击／死亡只打断该次工作，已完成工时和在制物留在设施；取消生产退回真实在制原料，已花工时不退。中途不能既退原料又保留成品。产物在设施输出中，必须真实取出和搬走。

首批不做自动多批循环；Agent 的共享蚁种代码负责重复启动。未来自动设备应作为独立真实能力注册，不能悄悄给所有设施增加免费自动生产。

## 9. 动作、API 与自由度

### 拟新增蚂蚁动作

| 动作 | 引擎负责的约束 |
|---|---|
| harvest(source_id,quantity) | 局部采收，成熟量／负载／冷却 |
| deposit(holder_id,item_id,quantity) | 将携带物放入真实容器 |
| withdraw(holder_id,item_id,quantity) | 从真实容器取出，校验负载 |
| transfer(ant_id,item_id,quantity) | 对近处友方活蚁转交 |
| work(building_id) | 推进施工／加工，受工作位和实际工时限制 |
| process(building_id,recipe_id) | 原子启动一个真实生产批次 |

旧 move_to、pickup_from、drop、deliver、attack、eat、follow、显式通信和认领继续保留。一次决策只有一个最终物理意图；不能在同次脚本中连续调用完成无限动作。持续 work／process 的忙碌与进度可查询。

DSL 数值句柄使用内容注册的稳定 ID，不按数组位置生成；旧 food_fruit 等可作为兼容别名。拟增加 item_id("fruit")、recipe_id("fruit_concentrate") 及局部／蚁后缓存查询函数，允许 Agent 根据目录自编策略。函数、遍历和动作均按明确规则计预算。

### 拟新增外部接口

- get_catalog：物品、设施、配方、身体模块、科技、已支持动作与参数说明，包含锁定原因。
- inspect_source、inspect_building、inspect_inventory：只读合法对象与最后观察值。
- plan_build、cancel_build、set_building_parameters：只管理计划和参数，不越过物理工作。
- save_game、list_saves、load_game、evaluate_program、get_statistics：支撑长期游玩与迭代。
- 后续 research、set_species_modules：约束内管理发展，作用仍由核心结算。

现有 observe、inspect_object、自由小组和蚁种程序更新继续复用。接口参数需定义错误、实际生效量、revision、世界实例与请求幂等；所有写入经过 Runtime actor。

### 信息约束

局部查询读取真实局部感知；远处查询最多读已经上传／下载的旧记录。能力目录公开不等于公开资源位置。设施由自己规划也不意味着远处库存变化实时可见。查看非法／未知 ID 不以不同错误泄露隐藏对象存在。

## 10. Agent 在游戏里如何组织一条产业链

例子：侦察蚁发现远处两个果丛与纤维源 → 显式上传 → Agent 在合法已知位置规划箱子和加工台 → 工蚁采纤维并送到施工点 → work 建成 → Agent 给各组设置 source_id／cache_id／processor_id 等自由参数。

所有搬运蚁仍执行同一份代码：根据本组参数，某组采果后放箱子，某组从箱子取果送加工台，某组 work 加工，另一组取成品回巢。兵蚁共享代码根据组地点守卫或巡逻。这里不引入引擎固定“采集工／搬运工／厨师”调度器。

每一步操作及失败原因可观察。Agent 对比直接回巢与加工后回巢的分支收益，可能拆掉无用中转、调整分组或回到简单直运。设施多不等于效率一定高。

## 11. M4：能力型科技和身体组合

科技以数据登记前置、成本、解锁能力；编写程序可以引用锁定动作，但执行返回 technology_locked，Agent 可提前规划。现有已能使用的基础动作不重新加锁。

原型方向：扩展设施类型／容器容量、更多可观察信息、受网络约束的协作存储、身体模块。先让每种蚂蚁共享一套身体配置，最多两个模块位；模块可改变质量容量、空载速度、负载惩罚、生命或视野，伴随明确代价。例如额外货囊更重、甲壳提高生命但降速。所有有效属性能由程序读取，不做纯装饰升级。配置切换有明确材料成本和冷却；改变生命上限不自动补满生命，只保留／夹紧当前生命，避免反复切换模块当作免费治疗。

可选计算储备按个体积攒：基础预算 B，每次决策最多存 B/2，储备上限 2B；程序显式申请本次额外额度，单次总预算不超过 2B。结算只扣实际超过基础预算 B 的指令，申请了但没用的额度不扣；基础预算剩余额按上限入库，不能通过重复申请重复存入。纯省预算的简单行为可以换一次复杂规划。必须先检查现有低预算算法是否足够，确认有需求再实现，不能默认用此掩盖程序错误。

这里的初值仅供原型评估。模块组合与计算储备分开交付，不需要同时上线。

## 12. M5：环境、挑战和长期目标

第一项环境机制只选昼夜，示例周期 12000 Tick（10 分钟）：白天果丛恢复较快，夜间更危险的肉类目标出现。具体倍率和事件配置化。环境相位、下一相位时间可读；地图外敌人的数量位置仍不公开。默认经营不限时，环境机制能作为场景开关。

挑战复用现有里程碑框架，新增真实指标：五分钟首次入巢点数、固定预算吞吐、连续供应、零死亡、限定人口等。比较条件包含种子、内容哈希、程序版本、开始检查点和样本时长，不只比较一个容易刷的数字。

更后期才做子蚁后开拓：旧殖民地保留，Agent 选择投入物资开新区域，代码和部分科技可复用，新环境要求重新规划。跨区域货物必须有明确运输方式，不让多个世界共享一个可凭空取用的无限库存。没有完整存档和单区域稳定经营前不做多世界迁徙，也不强制清档。

离线发展另开后续规格，运行的是已保存代码，不是 Agent 永久思考；有战斗和枯竭时必须真实模拟或采取明确简化规则，不能按历史收入直接发资源。

## 13. 画面如何表现

- 果丛显示少量果实图标和最近观察成熟量；纤维源显示可采材料图形，不展示未知源头。
- 箱子以箱子图标、容量条和分类库存显示；施工显示材料到达量与进度条。
- 加工台显示输入／在制／输出、当前配方、工作蚂蚁和停工原因。
- 蚂蚁携带标识显示物品类型，仍使用现有职业像素形象，不必一开始制作大量新动画。
- 玩家只看总览、对象详情、物流流向与统计，规划操作面向 Agent；不新增要求玩家手工安排每只蚂蚁的流程。
- 可选物流线只能来自实际转移记录或 Agent 明确标记；不能从隐藏资源真值自动画路线。

## 14. 对应现有工程怎么改

| 项目 | 变更 |
|---|---|
| Contracts | 类型物品／批次／容器／来源／建筑 DTO、状态与动作结果，存档包和实例标识 |
| Core | 源头生长、库存事务、施工、加工、计分与统计规则，统一配置校验 |
| Programs | 新感知结构、稳定内容 ID 查询、动作与工时预算；保留每蚁种共享编译程序 |
| Runtime | 世界唯一写入、管理计划与配方、版本校验、存读档一致点、合法投影 |
| Transport | 同步协议版本，分段读取／分页，避免新增账本导致突破当前 1 MiB 消息上限 |
| Mcp | 有文档的管理／查询／评估工具，世界实例、revision 与幂等参数 |
| Desktop | 源头／建筑绘制、对象观察和统计，不复制核心规则 |
| Evaluator | 加载检查点、相同 Tick 分支比较、多个种子，统一运行完整规则集 |
| Checks | 守恒、计分、缓存权限、并发、存档恢复、完整产业链和旧玩法回归 |

新增物体继续进入 Objects 的独立类型记录；物品数量所有权统一进入 ItemLedger，旧 Amount／Carry／Stock 逐步改为派生视图。不要直接修改现有 FoodStore 然后另加一份库存作为“缓存”。

拟定规则顺序：源头生长 2 → 局部观察 5 → 程序 10 → 通信 15 → 认领 16 → 跟随 19 → 蚁移动 20 → 敌移动 21 → 战斗 25 → 物品交互 30 → 工作推进 31 → 进食 32 → 地面刷新 40 → 发现 45 → 认领清理 46 → 统计 49 → 里程碑 50。以稳定 ID 解决同序规则，明确注册到 Desktop／Evaluator 共用的组合根；这是拟议排序，现有进食 31 等尚未调整。

源码内容分文件维护 items、sources、buildings、recipes、technologies、world 配置，均可数据扩展；新行为仍实现 IWorldRule。来源、批次、配方 ID 唯一并校验依赖，禁止使用系统时间或非确定性 Random。

协议与存档版本分开。当前 wire=11、content=9；每个实际交付阶段再递增并写迁移，不能把全部草案预先当作已经升级完成。M1 升级已有物品数据时：初始库存标记已结算，现有累计入巢保持历史基数，地面／携带食物在无巢穴提取机制的旧版本中视为尚未结算；若无法验证旧档来源，则拒绝自动猜测迁移。

## 15. 每阶段必须通过的验收

M0：同一存档恢复后推进相同 Tick，除实例 ID 和临时连接状态外世界一致；损坏文件、内容不匹配和坏程序不能破坏当前局；加载前命令不能误写新局；评估分支不改实局。

M1：果丛生长／满额／采空／冷却／多个蚂蚁抢同一份均正确；隐藏源头不泄露；源码与物品分账只创建一次原料；单类负载、掉落、治疗、交付继续守恒。

M2：箱子容量、部分存取、死亡、双向转交及同 Tick 冲突稳定；中转不计分，旧库存取出再送回不刷分；材料不足不能建成，取消不重复退款；所有工作实际花时间。

M3：输入不足／输出满拒绝启动；在制状态保存与恢复；打断／取消不同时产生退款和成品；加工品继承正确首次计分份额；建设→采收→转储→加工→回巢→进食完整链路通过。

每阶段运行全解决方案构建、原有 Checks 和新增检查；用真实 MCP 驱动桌面宿主验证一条实际流程，窗口存在不等于玩法验收。纯文档规划本轮不运行这些尚未实现的验收，也不冒称通过。

## 16. 交付边界

首个可开发任务建议为 M0。之后 M1、M2、M3 各单独可运行、可回退、可评估；三阶段完成后才称“第一版产业链经营”。所有原型值集中配置，试验允许某些组合明显更强，但复制资源、重复计分、越权感知和无成本无限增长必须修正。

本文件不改变用户既有三职业、共享代码、小组自由参数、显式动作、发现权限、无维护消耗及默认不限时经营的决定。后续如要改变这些基础约定，应单独写清对应玩法变化，不能在新系统中暗中加入。
