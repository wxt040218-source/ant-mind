# v0.10 食物、编队与补给实施方案

用户于 2026-11-08 授权：详细规划后开发。基线为 v0.9 战斗版本；本轮不重构引擎、不增加新职业、不替换模型、不推送远端。

## 玩法及数据

1. 自然刷新水果 fruit，敌人尸体为肉 meat。FoodType 与 Origin 独立；拾取、放下、死亡掉落、交付均保留类型。每次负载只装一种食物，容量仍为总份数，已有异类负载时跳过异类食物。巢穴库存按类型记账，总量为派生值。发展支出水果优先、肉其次，各一份等价；原最低储备约束保留。
2. 食物定义注册在配置：ID、显示名称、每份回血量；首版水果 3、肉 6，可扩展类型。初始库存全部水果。新增累计食用数量和实际恢复生命统计；累计交付维持历史毛交付含义，吃饭不增加交付分数。世界守恒包含地面、携带、库存、发展支出和食用消耗。
3. 小组有稳定 ID、名称、任务说明、集合点、目标点、撤退点和命令版本；最多 32 组。每只活蚁只能属于一组，可以随时调入、调出；死亡记录保留归属。UI 和 MCP 均可创建、改名、解散、调整任务点、添加或移除任意活蚁。
4. 执行优先级为小组×蚁种程序覆盖 > 全群蚁种程序。共享大脑与身体属性仍按原规则。组程序独立校验、版本及回滚；部署／回滚清空相关个体记忆与旧目标。未设置覆盖时实时沿用全群程序。管理操作和代码部署与既有管理 API 一样直接生效；集合／任务／撤退坐标只能通过显式 request_queen_info 获取，断网仍执行最后收到的同组任务。调整成员时清除旧组缓存，防止跨组携带任务。
5. 小组不会自动形成阵型、自动攻击或自动采集。DSL 提供小组缓存、局部队友，以及 follow(id,distance) 基础动作；引擎检查视野和距离，朝最近一次可见队友位置移动。程序自行决定等待、护送、冲锋、撤退。

## 进食与战斗顺序

- eat(type) 每次吃一份，type 数字使用 food_fruit / food_meat 常量。优先使用同类携带食物；无同类携带时，仅巢穴一格内可从库存吃，仍不能跌破最低储备。
- 进食 40 Tick（2 秒），期间不移动、不决策、不攻击。完成时才扣食物和增加生命，不超过 MaxHealth；满血或没食物明确失败。不复活，不给蚁后自动回血。
- 战斗结算早于进食。受伤会取消正在进行的进食；本 Tick 受击不能开始进食。被打断不扣食物。库存食物不预留，结束时再次原子检查，不足则失败，避免多只蚂蚁重复消费同一份。
- 默认兵蚁补给策略与可复制的编队示例体现低血回巢、进食、再出发；不强制所有用户程序撤退。

## 资源认领

- claim_food(id,quantity,ttl) / release_claim() 为显式协作请求，不替代 pickup；每蚁最多一项，quantity 1～100，ttl 1～1200 Tick。
- 只能认领局部真正看见的食物，稳定 ID 顺序分配剩余可认领数量；死亡、退出／换组、到期或食物耗尽清理。认领是建议，其他程序仍可直接拾取。
- 个体读取局部认领，蚁后范围内显式获取认领快照；离线缓存允许过期，不从世界真值偷偷刷新。玩家和外部 Agent 可看本群认领，未知食物不因此暴露。

## 阶段与验收

1. Contracts/Core：类型化库存、类型保真运输、治疗状态与规则；检查肉不会变水果、混装拒绝、死亡掉落、消费守恒、满血、打断、并发库存和最低储备。
2. Runtime/Programs：编队管理、程序覆盖与回滚、通信缓存、认领、跟随及 DSL；检查越界／非法组／死成员、请求幂等、组间隔离、断网旧任务、默认回退、认领到期和预算。
3. Desktop/MCP：库存明细、小组页面、成员选择、任务点、按蚁种代码查看／部署／回滚、个体归属／进食状态；全部按钮走同一 Runtime 命令。
4. 集成：默认玩法与原检查回归、战斗采肉运输疗伤完整链路；构建和 Checks。运行进程与实际窗口检查分别记录，重启前保留当前可读取快照（完整存档仍未实现）。

协议／内容版本同步升级，更新 API、DSL、框架、交接与项目状态。发现不变：所有食物和敌人继续经过权限投影，蚂蚁程序只接收局部感知及显式通信缓存。


## 实施结果（2026-11-08）

四阶段已完成：规则、编程／Runtime、UI／MCP和集成。协议 10、内容 schema 9；构建 0 警告／0 错误，183 项检查通过；实际桌面创建混编组并通过 MCP 激活三个组程序，T2506 三名组员收到任务，全部蚂蚁无程序错误。完整采肉、交付、进食和守恒为自动集成证明，实局本段尚未进食。详见 PROJECT_STATUS.md。

实现细节：ClearGroupProgram 为立即管理操作，会清除覆盖历史，界面有提示；单次负载只装一种食物。认领为建议而非强锁，拾取成功释放自己的认领，45 后清理死亡／耗尽记录及裁剪余量。程序改动和管理分组与既有即时管理一致，任务点仍依通信缓存。32 组满载与长时间运行性能尚未专门验证。
