# Ant Mind｜最小游戏规格 v0.3 草案

状态：历史讨论稿，已由 docs/MVP_SPEC.md v0.3 取代；保留本文记录草案形成时的内容。
依据：用户在“设计蚁群底层规则”对话中确认按蚂蚁种类编程，并提出先有寻找资源蚁和搬运蚁；寻找资源蚁也能少量搬运，但负载时更慢。
本文把已有 v0.2 决定继续作为默认基线；明确标注为“建议值”的项目仍可调整。

## 1. 项目目标

Ant Mind 是让外部 AI Agent 编写蚁群行为程序的无引擎模拟游戏。玩家给出发展目标，Agent 通过 MCP 查看获准的信息、编写和测试程序，并观察蚁群的实际结果。

长期方向是让不同程序在同一组物理、资源和信息规则下，形成不同的探索、运输、通信与分工策略。游戏提供规则和可观察结果，不预设唯一正确算法。

核心编程单位是蚂蚁种类：同一种类的所有蚂蚁使用该种类当前的共同程序；每只蚂蚁仍有独立位置、负载、感知、记忆和决策状态。Agent 不为单只蚂蚁上传专属代码。

## 2. 本版范围

首批提供两种可编程种类：

- 侦察蚁（Scout）：主要探索并发现资源，也能少量搬运。
- 搬运蚁（Hauler）：主要运输较多资源，也能自行感知、寻找和采集资源。

两种蚂蚁都可以完成资源采集闭环；身体参数和种类程序让它们有不同优势。游戏不把“侦察”与“搬运”写成不可改变的硬性职责。

这一版保留原型的单张平面地图、固定蚁巢、一种资源、通用信息素、持续经营和无胜负倒计时。暂不加入障碍、碰撞拥堵、体力、饥饿、死亡、维护成本、生产链、建筑或多人竞技。后续可以把这些规则作为独立扩展逐项加入。

## 3. 初始身体类型

下表数值沿用 v0.3 讨论中的原型建议，用于形成可测试的差异，不是经过平衡验证的最终值。均须放在内容配置中，不能由蚂蚁程序自行改写。

| 属性 | 侦察蚁 Scout | 搬运蚁 Hauler |
| --- | ---: | ---: |
| 空载速度 | 150 固定点单位/Tick | 120 固定点单位/Tick |
| 满载速度 | 90 固定点单位/Tick | 100 固定点单位/Tick |
| 负载上限 | 1 单位 | 4 单位 |
| 感知半径 | 6 格 | 3 格 |
| 主要优势 | 探索范围与速度 | 单次运输量与满载效率 |

坐标仍采用每格 1000 个固定点单位、模拟频率 20 Tick/秒。满载速度指达到该种类负载上限时的速度；中间负载的速度计算方式需由 Core 固定并纳入测试。以上速度和负载数值应可调整。

侦察蚁发现资源后，可自行决定少量带回，或用信息素留下路线信号，让搬运蚁自行发现并决定是否前往。Core 不替 Agent 自动分配任务。

## 4. 种类程序与个体状态

### 4.1 程序槽位

系统初期有两个独立的种类程序槽位：侦察蚁程序和搬运蚁程序。每个槽位各自保存当前版本、版本历史、修改理由和默认回退版本。

Agent 提交程序时必须指定种类。更新一个种类的程序只影响该种类的成员，不更改另一种类的程序。成功校验的版本在模拟 Tick 边界统一生效；校验失败时拒绝该版本，旧版本继续运行。

继续使用受限文本 DSL：变量、条件、有限循环、感知、动作和有限记忆操作均按确定的指令成本计费。禁止任意 C#、文件、网络或操作系统访问。超预算或执行错误时，结束该蚂蚁本次决策并记录原因，保留此前已生效的合法动作。

### 4.2 个体独立性

同一种类的蚂蚁共享程序版本，不共享运行时记忆。每只蚂蚁独立保存位置、携带量、当前目标、程序记忆、决策间隔和交互冷却。

沿用 v0.2 的有限记忆初值：每只蚂蚁有 16 个有名称的数值槽。个体程序不能直接读取其他蚂蚁的记忆。程序替换或回滚时，清空被更新种类成员的程序记忆和旧目标；保留位置、携带量及世界状态。

### 4.3 身体规则与程序边界

程序决定探索方向、资源目标、移动目标、拾取、交付及信息素操作。Core 按该蚂蚁种类的速度、感知范围和负载上限结算移动与动作，并拒绝超载、距离不符、资源不足或违反冷却的操作。

到达资源点或蚁巢不会自动拾取或交付。重复提交相同移动意图不能提高引擎结算速度。两种蚂蚁都能执行合法的探索、拾取、回巢和交付动作，程序负责选时机。

## 5. 信息、发现与协作

- 每只蚂蚁只获得种类感知半径内的信息；感知范围由身体配置决定。
- 玩家可看全图；Agent 信息权限仍可切换为“仅已发现”或“全图”。切回局部权限不能让 Agent 忘记之前已读取的全图信息。
- 一只蚂蚁发现资源不会把资源坐标自动广播给另一只蚂蚁。Agent 的发现记录也不自动变成任何蚂蚁的局部感知。
- 沿用单一共享信息素通道，浓度含义由种类程序自行约定。程序决定何时释放、读取和如何跟随；信息素只衰减、不扩散，操作计入指令预算。
- 两种蚂蚁可以通过信息素留下路线或信号，再由另一种类的程序在局部范围内读取并作出决定。Core 不解释信号语义，也不保证信号能传递任意坐标或消息。

这使侦察蚁的策略可以在“自己运回少量资源”和“留下线索、让搬运蚁运输”之间权衡；搬运蚁也能在没有线索时自行探索。

## 6. 增员、升级与经营

沿用 v0.2 的公共库存、最低储备约束、人口上限、五级计算预算、决策频率、资源补充和累计交付统计。

Agent 增员命令需要指定侦察蚁或搬运蚁。初始建议继续使用相同增员成本和同一总人口上限，避免首轮同时改变经济规则；Agent 在玩家约束内决定两种蚂蚁的数量比例。是否为不同种类设置独立费用或人口上限留待后续验证。

初始建议沿用一个全群共享的大脑等级：两种程序使用同一等级对应的指令预算和决策间隔，身体速度、感知与负载仍按种类不同。后续可根据测试结果再决定是否分种类升级。

游戏不加入饥饿、死亡或维持消耗。资源仍可用于增员和升级，满级后继续经营。

## 7. MCP 与桌面观察

MCP 至少需要支持：

- 查询两种蚂蚁的属性、数量、程序版本和运行统计。
- 按种类查看 DSL 说明、查询当前程序、校验和提交程序、查看版本历史并回滚。
- 获取权限允许的世界信息、资源统计、蚂蚁状态和决策记录。
- 查询单只蚂蚁的状态用于调试；这不提供单体代码槽位。
- 按相同种子和模拟时长运行评估，比较程序版本和蚁种比例。

桌面界面显示两种蚂蚁的数量、外观、负载和状态；分别查看两份程序及版本；选中个体时显示其目标、感知摘要、记忆、最近决策分支、预算消耗和错误；统计按种类展示交付量与效率，同时显示蚁群总计。

保留暂停、单步、1／2／5 倍速、存读档、地图种子、最低储备、人口上限、Agent 信息权限和信息素覆盖图。存档应保存种类定义、两种程序版本、个体种类、独立记忆及随机状态。

## 8. 技术与兼容要求

- 保留现有 .NET 10、C# Core、Avalonia、官方 MCP SDK、确定性 20Hz 仿真、固定点坐标及九项目分层。
- Core、Programs、Contracts 不依赖桌面 UI 或 MCP SDK；世界状态仍只由 Runtime actor 写入。
- 用稳定的蚂蚁种类标识和配置定义描述身体参数；种类程序及其管理按标识路由。首版只启用 Scout 和 Hauler，为后续增加种类留出明确扩展点，不提前实现插件市场或任意动态装载。
- Agent 程序只能读取由该只蚂蚁 Perception 提供的信息，不能借种类程序接口读取玩家全图投影或完整 WorldState。
- 新规则通过项目现有的 IWorldRule 和稳定排序接入；所有世界状态和命令结果保持确定性。
- 开始实施前检查本地源码、Git 状态和现有检查；保护工作区未提交改动，不以旧远端版本覆盖本地内容，不擅自推送 GitHub。

## 9. 实施顺序

### 阶段 A：双类型世界基线

1. 盘点 v0.2 单一工蚁、全局人口和单程序接口与本草案的差异。
2. 增加配置化的 Scout、Hauler 身体定义及个体种类标识。
3. 使移动速度、负载校验、感知范围和生成命令按种类工作。
4. 保留既有默认采运闭环，并提供两种都可运行的默认程序。

### 阶段 B：按种类编程闭环

1. 建立每种类独立的 DSL 程序版本槽、校验、Tick 边界替换、回滚和错误记录。
2. 保证同类共享程序、个体记忆隔离、定向更新不影响另一种类。
3. 通过 MCP 按种类读写和诊断程序。
4. 在桌面界面展示双类型数量、状态、程序和统计。

### 阶段 C：同条件评估

提供可重复的固定种子评估和不同侦察蚁／搬运蚁比例对照。报告累计交付、单位模拟时间交付量、各类蚂蚁贡献、平均运距和指令预算；不得把人口或升级投入变化造成的差异全部归因于算法。

体力、资源差异、障碍与拥堵、多通道信息素、资源加工、设施和环境周期属于后续独立阶段，不作为本轮实现前置条件。

## 10. 验收标准

1. 世界中可同时存在两种蚂蚁，且可分别增员、统计和选中观察。
2. 两种蚂蚁的移动速度、负载上限和感知半径按配置分别生效；侦察蚁少量负载时速度下降。
3. Scout 和 Hauler 各有可运行的默认 DSL 程序，均能完成合法采集和交付；Hauler 也可以自行发现资源。
4. 同类蚂蚁共享对应种类的程序版本，但个体记忆隔离；更新 Scout 程序不会改变 Hauler 程序或其成员状态，反之亦然。
5. Agent 不能通过程序槽、MCP 或个体感知绕过已配置的信息权限。
6. 拾取、交付、超载、预算、程序错误、版本应用和回滚均有自动检查覆盖。
7. 同种子、同配置、同程序和同操作序列得到相同仿真结果；原 M2 已有检查继续通过或在迁移中作出可追溯的替代。
8. 可以按相同起点比较两种类比例或程序版本，并输出可核对的统计结果。
9. 构建、项目检查、无界面评估和实际 MCP 调用分别报告结果；进程调用不声称等同当前 Codex 会话已连通。

## 11. 与 v0.2 的主要变化

| v0.2 已确认内容 | v0.3 草案调整 | 处理建议 |
| --- | --- | --- |
| 只有一种工蚁 | Scout 与 Hauler 两种身体类型 | 作为本草案核心变化 |
| 全体工蚁共用一份程序 | 每个种类各有一份共享程序 | 个体不再有专属程序 |
| 速度、负载、感知范围统一 | 这些身体属性按种类配置 | 本草案先用可调建议值 |
| 增员不选择类别 | 增员命令指定种类 | 总人口上限先维持共享 |
| 程序更换清空所有工蚁记忆 | 只清空被更新种类的成员记忆和目标 | 维持原重置原则并限定影响范围 |
| 一个大脑等级供全体使用 | 初版建议仍全群共享等级 | 先不引入种类独立升级经济 |

v0.2 文件作为历史规格保留；正式实施基线见 docs/MVP_SPEC.md v0.3。

## 12. 待用户审阅的原型提议

本草案阶段列出的部分数值是供讨论的建议；正式实施基线及当前可调初值见 docs/MVP_SPEC.md v0.3：

- 身体参数表中的速度、载重和感知半径。
- 满载和部分负载之间采用何种速度插值公式。
- 首版继续使用全群共享大脑等级与同一升级费用。
- 两种蚂蚁继续使用相同增员成本，并共用一个总人口上限。
- 两种类的默认 DSL 程序如何利用单通道信息素协作。

建议 Work 先实现配置化参数和清楚记录迁移，再用基准程序验证参数，不将建议数值写死在核心逻辑里。
