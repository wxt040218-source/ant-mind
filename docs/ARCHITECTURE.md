# 技术架构草案

状态：设计建议，尚未实现，也未最终选型。

## 分层

```text
玩家的发展方向
      ↓
AI 总指挥：战略计划、职业分配、优化任务
      ↓
职业程序生成：程序版本、变更理由
      ↓
校验与试运行 → 职业程序运行时
      ↓
固定步长模拟：移动、采集、搬运、交付、繁殖
      ↓
状态快照、指标、事件日志 → AI 总指挥 / 玩家界面
```

大模型在战略调整和职业程序更新时调用。蚂蚁的逐 Tick 行动由本地程序运行时执行，同职业共享程序，各个体保存自己的状态。

## 模块边界

| 模块 | 责任 |
| --- | --- |
| 模拟核心 | 固定 Tick、可设种子的随机数、资源与蚂蚁状态、动作结算 |
| 职业运行时 | 校验程序、计指令预算、维护记忆、输出合法动作 |
| AI 适配层 | 把目标和允许的状态整理成输入，接收结构化战略与程序 |
| 挑战与记录 | 配置初始条件、记录程序版本和操作、计算成绩、回放 |
| 可视化界面 | 像素地图、分工统计、目标输入、程序对比与错误反馈 |

AI 和职业程序通过明确的观察与动作接口操作世界，不能直接更改库存、坐标或分数。程序只能读取其等级和职业允许的信息。

## 程序执行方案

原型拟使用受限 DSL／结构化指令树，提供条件、目标选择、移动、采集、装载、交付等能力。AI 能组合这些能力形成职业程序；内置程序使用同一套接口作为基线。

执行前验证结构、动作权限和版本。执行时限制指令数、记忆量和查询成本，超预算或异常时返回可记录的错误与确定性的等待动作，保留上一可用版本。避免直接执行模型生成的任意 JavaScript，也不能仅靠 Web Worker 充当安全边界。

路径查询等引擎服务需要有界输入与可计费成本，不能通过一个指令绕过整个计算预算。

## 可重现性

模拟与渲染分离，固定 Tick，使用有种子的伪随机数。模型输出本身未必可重复，因此需要记录实际应用的战略、程序内容及生效 Tick，而不是只保存聊天提示词。

同一初始配置、规则版本和操作日志应能重放相同的交付结果。程序比较必须从相同起点重新运行，不能只比较不同阶段的短期吞吐量。

## 技术选择与 AI 接入

前一轮讨论提出浏览器版本、TypeScript 模拟层和 2D 渲染引擎的方向；Phaser 是候选，具体框架与版本待原型开始时确认。模拟核心应能脱离画面执行，以便验证规则和评估策略。

先通过内置策略验证闭环，再替换为真实模型适配器。模型服务商、调用费用和部署方式尚未确定。密钥不进入仓库；采用托管服务时由服务端持有密钥，客户端仅访问受限的游戏接口。先保持小规模与按需调用，测出延迟、费用和有效改进率。

以后可提供面向外部 AI 的观察／动作接口，让聊天助手或其他 Agent 直接参与挑战。具体协议与接入方式留待最小闭环成立后设计。
