# Ant Mind 游戏内核调研与候选方案

调研日期：2026-11-08，Asia/Shanghai。按“放置／经营／增量／蚂蚁题材”理解需求。以下事实来自游戏官方 Steam 商店页和官方文档；机制迁移、数值、接口和实施顺序是本项目建议，不代表参考游戏原本这样实现。未实际安装试玩这些竞品，不把商店介绍当作完整玩法验证。

## 结论

Ant Mind 最适合发展为：发现并经营食物来源 → 编程组织采运和防御 → 建立加工与物流 → 用成果解锁新能力 → 到新环境重组策略。玩家给方向，外部 Agent 负责全部规划；同种蚂蚁始终共享代码，小组只提供不同数据。不是把这些游戏的手动管理面板搬进来。

首选稳定食物源、物流中转和小型生产链；随后做能力型科技、可组合身体特性和环境变化。跨世代重生／迁徙最后考虑，先补完整存档。不建议优先堆更多相似职业、纯倍率升级或强制清档。

## 当前项目真正缺少的东西

现有采运、战斗、类型食物、治疗、自由小组、通信和预算已经具备，但正式地图 128×128，仍主要依靠随机小资源持续补充；水果／肉在发展支出中大体等价。此前连续六个一分钟实玩窗口分别交付 8／6／3／14／2／5，世界状态连续变化，中间策略还出现预算错误，不能据此宣称任何一项改动可靠增产。

研究判断：增加更多职业之前，应先让资源来源可经营、生产有不同用途，并提供能归因的效率反馈。不同算法有条件发挥，才会产生长期优化乐趣。这是本项目分析，不是竞品评分能直接证明的结论。

## 候选一：从“随机食物点”扩展为“可经营食物源”——最高优先级

参考蚂蚁游戏的生态资源取舍，设计独立 FoodSource 对象：类型、位置、储量、成熟数量、恢复周期、是否发现、最近观察时间。已有单份地面食物继续为独立 Food 对象，避免把原 1～5 容量约定直接改成无限大。

- 果丛：低风险、周期结果，可以长期规划采集路线。
- 掠食者活动区：高风险肉类来源，兵蚁清除威胁，搬运蚁及时收集尸体。
- 后续可选：蚜虫群持续产蜜，保护它才有稳定收入；菌圃消耗原料生产食物。

收益：同一地点值得反复经营，侦察的发现能持续服务运输。Agent 可以选择游击搜寻、驻点采集、区域巡逻或狩猎。

接口候选：局部感知食物源、读取成熟量、显式 harvest(source_id)、上报来源信息。恢复属于世界规则，实际采收必须由代码发动作；未发现来源和视野外变化仍隐藏。资源源头、地面物品和搬运状态只保留一份权威记录。

## 候选二：中转储物点＋明确转交——最高优先级

借鉴工厂游戏的物流瓶颈，新增有位置、有分类库存、有容量的缓存对象。提供 deposit、withdraw、transfer 等基础动作，小组参数可记录节点 ID 或命名地点，Agent 自己形成采集线和运输线。

这不是自动调度系统，不会替 Agent 规划路线。相同能力的工蚁增加中转也不保证更快；交接有时间与搬运成本，只有减少绕路、改善批量运输或形成补给时才可能获益，应通过实验比较。

反刷分要求：中转不等于进巢，不直接增加累计交付；曾入巢食物被取出后不得重复交付计分。若支持从公共库存取货，必须跟踪已计分份额或食物批次来源，不能只比较总库存。持有者切换、放下、治疗、加工都必须满足按类型守恒。

## 候选三：食物用途差异＋最小生产链——最高优先级

参考 Melvor 和工厂经营，不把水果／肉仅作为两种颜色：

- 基础发展：保留水果可产通用卵和第一批兵蚁，避免没有肉→没有兵蚁→永远无法取得肉的循环依赖。
- 蛋白质：肉用于后续身体强化或高级繁殖配方。
- 加工：果实可加工成高密度补给，肉可加工成恢复效率更高的食物；是否划算由产出、工时与运输成本决定。
- 后续材料：纤维供巢室、缓存点或设施建设。初版不同时引入大量新资源。

建议先只有一个加工设施和两份配方。Agent 通过代码明确建设／运入／加工／运出，不能靠管理命令让未送到的物资凭空出现在设施里。

加工增加的是可追踪的物品转换或营养价值，不能把“原始资源采集量”简单随配方产出份数提高，避免分装／加工刷分。

## 候选四：科技解锁新的操作能力——第二阶段

参考编程增量游戏，保留现有五级预算／决策频率，但增加能改变策略结构的能力。例如局部物品转交、受约束的小组协作存储、设施操作和更复杂传感器。已有功能不应为了制造进度而重新锁回去。

可选计算额度储备：将未用指令以有上限的方式积攒，供下一次复杂决策使用，形成“便宜巡逻＋偶尔重规划”。必须按确定性指令计费、限制每次突发上限、明示存量和支出，不能变成绕过执行预算的漏洞。

所有能力通过蚁群网络／科技等级注册，保留显式操作、冷却、距离和信息范围。更强的 API 不等于直接开放未知资源坐标。

## 候选五：可组合身体特性——第二阶段

借鉴构筑与增量游戏的组合：携带模块、移动模块、甲壳、感知器官等改变身体属性和代价。Agent 决定配置，不给玩家增加“请选择采集流派”的流程。

首轮可先按蚁种共享配置，沿用现有同类共享升级与代码。若将来允许同类不同身体实例，代码读取个体属性分工，仍不产生每只蚂蚁独立代码。优先增加不同策略成立的条件，不追求所有收益相等；只限制无成本无限收益等明显退化解。

## 候选六：环境周期和多目标挑战——第三阶段

参考蚂蚁生态和 Against the Storm，逐步加入确定性的昼夜、天气或资源季节。夜间狩猎、白天采果等是可选设计示例，不是已经决定的具体规则。

环境必须能被观测并适度预测，不能全靠无提示随机惩罚；远处事件不能泄露未知对象。挑战可比较原始食物入库速度、营养净收益、零伤亡持续供应、最小蚁数或有限计算预算。现有里程碑已存在，扩展目标语义即可，不重复做一套计数器。

默认不限时经营继续保留，挑战规则作为可选场景。闭环足够丰富后才做迁徙／子蚁后开拓：保留旧殖民地、代码和部分科技，进入新环境，不直接强制抹掉玩家长期积累。

## 增量与放置的边界

先补完整保存／继续游戏，确保长期积累真的能留下。之后再讨论离线结算：离线运行的是已保存程序，不是外部 Agent 持续思考；若有战斗、死亡和枯竭，不能用“过去一分钟产量×离线分钟数”粗略发资源。

重生机制暂后置。与其重复清零获得一个全局倍率，更值得新增能改变路线、运输、生产和计算决策的规则。

## 建议实施顺序与验收

1. 前置：完整存档；保留程序版本和随机状态。补每个模拟分钟的交付、净变化、移动／交互／空闲时间、失败动作和预算使用，提供给 Agent。玩家看到概览即可。
2. 第一批玩法：果丛／资源源头 → 缓存点与转交 → 单设施两配方，逐项通过守恒和权限检查。
3. 第二批：能力型科技、身体特性、小组共享存储／计算储备中的合适部分。
4. 第三批：环境周期、多个挑战场景，再评估迁徙和长期局外成长。

所有场景用相同起始存档／随机状态进行分支比较，覆盖多个种子和多个一分钟窗口，不能直接把连续不同世界的收益差解释成策略改进。倍率仅影响等待，不改变每分钟模拟时间的定义。不得用重复搬运、转储、分装或加工虚增资源获取量。

工程延续 IWorldRule 稳定排序、Runtime 唯一写入、配置注册、独立对象、受限投影；新动作进入 DSL，外部管理与查询开放 MCP。UI 不负责策略规划，同类继续共享代码。本文为候选设计与实施建议，本轮没有修改运行中的世界或实现这些新机制。
